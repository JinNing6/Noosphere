# Noosphere v0.9.0 Concentrated Launch Pack

Status date: 2026-07-20

## Current Decision

Noosphere is ready for a concentrated developer launch through GitHub, PyPI, Codex,
Claude Code, and MCP communities. The Android application remains a secondary exploration
surface and does not block the developer launch.

The campaign uses one promise:

```text
Install once. One Agent learns. Every Agent inherits the Skill.
```

One primary call to action:

```bash
codex plugin marketplace add JinNing6/Noosphere
```

Do not lead with the 3D universe, consciousness philosophy, Android application, 45-tool
count, or a request to contribute. Those remain available after the user understands the
automatic Live Skill workflow.

## 72-Hour Sequence

### Hour 0-6: Preflight

- Merge the README and launch-asset PR after all quality gates pass.
- Upload the 1280 x 640 social preview in GitHub repository Settings.
- Verify every public install command from a clean environment.
- Open the README in GitHub desktop and mobile widths; confirm the message, install command,
  demo, and first real Skill are visible without opening the old universe section.
- Prepare personal availability for technical replies during the English launch window.

### Hour 6-24: English Developer Launch

- Publish the five-post X / LinkedIn thread with the MP4 attached.
- Submit Show HN with the repository as the destination.
- Publish one rules-compliant technical post in the most relevant MCP or coding-Agent
  community; do not spray identical copy across several communities.
- Pin or prominently link the `v0.9.0` release and Living Skill #001 evidence.

### Hour 24-48: Chinese Developer Launch

- Publish the technical case to V2EX or the best matching active developer community.
- Publish a deeper implementation article on 掘金 only after adapting the copy to that
  community; do not reuse the short forum post verbatim.
- Lead with the artifact-runtime failure and automatic Skill inheritance, not product vision.

### Hour 48-72: Evidence Follow-Up

- Answer every substantive technical question with a direct code, registry, digest, or test link.
- Record real outcomes and external evidence without inferring adoption.
- Publish one follow-up only if it contains new evidence: a real install, a failure boundary,
  an outcome, an update candidate, or a maintainer response.
- If the launch produces no completed install or query feedback, inspect the first-result path
  before opening more channels.

## Conversion Path

```text
specific repeated failure
-> repository first screen
-> one install command
-> automatic Live Skill discovery
-> digest verification
-> local project verification
-> optional public outcome
-> reviewed Skill update
```

At each stage, present one next action only. Do not place install, validation, upload,
Android, 3D universe, share proof, and Discord as competing calls to action in the same post.

## Success Metrics

The product north star remains `Weekly External Verified Reuses`.

For the first 72 hours, record:

- repository unique visitors;
- Stars;
- official PyPI downloads;
- reported install attempts;
- successful read-only queries;
- success, partial, and failure Outcomes;
- external maintainers or developers who provide linked evidence.

Do not treat Git clones as people, downloads as active users, Stars as successful reuse, or
social impressions as product activation.

## Stop Conditions

Pause channel expansion and repair the product surface if any of these occur:

- public v0.9.0 installation fails;
- automatic control Skill is not loaded after installation;
- the first useful result takes longer than 60 seconds because of avoidable onboarding;
- the README claim exceeds the current `maintainer-validated` evidence level;
- several visitors ask the same basic positioning or installation question;
- the launch attracts broad curiosity but no real queries, installs, or outcomes.

The next launch event should be a real external Outcome or a reviewed new Skill version,
not another generic announcement of the repository.
